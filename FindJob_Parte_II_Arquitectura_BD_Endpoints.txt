# 1. Contexto y alcance

FindJob es una plataforma web de contratación de servicios entre personas. Permite explorar servicios remotos y presenciales, publicar ofertas profesionales, enviar solicitudes, coordinar la ejecución, comunicarse mediante chat interno, registrar pagos y comisiones, calificar servicios finalizados y gestionar mecanismos de seguridad para trabajos presenciales.

El diseño prioriza la cadena funcional **persona → perfil → servicio → contratación → comunicación → ejecución → pago → calificación**. La solución se plantea sobre Google Cloud Platform.

## 1.1 Alcance funcional cubierto

- Registro e identificación de usuarios con roles múltiples.

- Perfil profesional del trabajador, habilidades y cobertura geográfica.

- Catálogo de categorías, subcategorías, servicios y modalidades.

- Exploración pública de servicios y perfiles.

- Solicitudes de servicio únicamente por usuarios autenticados.

- Programación de citas presenciales o remotas.

- Chat interno asociado a solicitudes aceptadas.

- Archivos adjuntos referenciados desde Cloud Storage.

- Pagos internos inicialmente simulables y aplicación histórica de políticas de comisión.

- Calificaciones posteriores a la finalización de la cita.

- Chequeos y alertas de seguridad para servicios presenciales.

# 2. Limitaciones y restricciones técnicas

| **Restricción / decisión** | **Definición**                                                                                                                                                            |
|----------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Base de datos              | Debe ser relacional SQL. Se adopta PostgreSQL 17 sobre Cloud SQL.                                                                                                         |
| Normalización              | El modelo se diseña hasta 3FN, evitando duplicidad y atributos derivados innecesarios.                                                                                    |
| Acceso a datos             | El frontend no se conecta directamente a Cloud SQL. Toda interacción pasa por el backend/API.                                                                             |
| Transporte                 | Los servicios expuestos al frontend deben operar sobre HTTPS. Cloud Run y Firebase Hosting proporcionan endpoints seguros administrados.                                  |
| Autenticación              | La exploración puede ser pública, pero crear solicitudes/postularse requiere usuario autenticado. La autenticación se delega a Identity Platform/Firebase Authentication. |
| Credenciales               | La base de datos no almacena contraseñas de usuarios; conserva únicamente el UID externo de autenticación y datos de negocio.                                             |
| Roles                      | No existe un valor AMBOS. Un usuario puede tener múltiples roles mediante usuario_roles.                                                                                  |
| Modalidad                  | No existe modalidad AMBOS. Un servicio se relaciona con una o más modalidades mediante servicio_modalidades.                                                              |
| Archivos                   | No se almacenan BLOB en PostgreSQL. Los binarios se ubican en Cloud Storage y SQL conserva metadatos y ruta.                                                              |
| Pago                       | En el alcance académico la pasarela puede simularse. El modelo conserva monto, método, estado y política de comisión.                                                     |
| Seguridad presencial       | Las alertas y chequeos pueden simularse; no existe integración obligatoria con organismos de emergencia.                                                                  |
| Moneda                     | El alcance actual asume valores monetarios en COP. No se modelan divisas ni conversión monetaria.                                                                         |
| Pago por cita              | El modelo actual admite como máximo un pago por cita, suficiente para el MVP académico.                                                                                   |
| Calificación               | Se permite una calificación por cita y únicamente después de finalizarla.                                                                                                 |
| Chat                       | Una conversación se asocia a una solicitud aceptada y sus participantes válidos son cliente y trabajador.                                                                 |
| Alta disponibilidad        | La instancia actual de desarrollo usa zona única; no equivale a una configuración empresarial multi-zona.                                                                 |

# 3. Arquitectura e infraestructura tecnológica

Para el alcance del proyecto se recomienda un **monolito modular** en lugar de microservicios independientes. Esta decisión reduce complejidad operativa y costos sin renunciar a una separación interna por dominios funcionales.

## 3.1 Criterios de arquitectura y justificación

Se adopta un monolito modular en Cloud Run en lugar de microservicios independientes. Para el alcance académico y el volumen inicial esperado, los microservicios añadirían complejidad de despliegue, observabilidad, comunicación entre servicios y costos sin un beneficio proporcional. La modularidad se conserva dentro del código separando dominios como usuarios, perfiles, servicios, solicitudes, citas, chat, pagos, calificaciones y seguridad. Esta decisión favorece mantenibilidad y evolución progresiva \[1\], \[12\].

La separación entre frontend, backend y base de datos es también una decisión de seguridad. El navegador nunca se conecta directamente a Cloud SQL ni recibe credenciales de PostgreSQL. Toda operación pasa por FastAPI, donde se valida identidad, autorización, entrada y reglas de negocio antes de acceder a la persistencia.

| **Componente**                              | **Por qué se implementa**                                                                     | **Aporte al proyecto**                                                                |
|---------------------------------------------|-----------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------|
| React + TypeScript + Vite                   | La aplicación requiere múltiples pantallas, filtros, formularios y componentes reutilizables. | Facilita una SPA mantenible y reduce errores de integración mediante tipado estático. |
| Firebase Hosting                            | El frontend compilado es contenido web estático y debe publicarse de forma segura.            | Entrega HTTPS administrado y despliegue sencillo \[4\].                               |
| Python + FastAPI                            | La API debe exponer servicios REST, validar datos y aplicar reglas de negocio.                | Permite desarrollo rápido, validación estructurada y documentación OpenAPI.           |
| Cloud Run                                   | Se requiere ejecutar el backend sin administrar servidores.                                   | Endpoint HTTPS y escalado administrado \[1\].                                         |
| Cloud SQL for PostgreSQL                    | El proyecto exige SQL relacional y un modelo en 3FN.                                          | Transacciones, integridad referencial y administración simplificada \[2\].            |
| Identity Platform / Firebase Authentication | Debe distinguirse navegación pública de acciones protegidas.                                  | Centraliza autenticación y evita almacenar contraseñas en la base de negocio \[3\].   |
| Cloud Storage                               | Perfiles y chat pueden manejar imágenes y documentos.                                         | Separa binarios de datos transaccionales y evita BLOB en PostgreSQL \[5\].            |
| Secret Manager                              | Credenciales y API keys no deben residir en el código.                                        | Reduce exposición de secretos y permite controlar acceso por IAM \[6\].               |
| Cloud Logging + Monitoring                  | Se requiere trazabilidad de errores, rendimiento y seguridad.                                 | Facilita diagnóstico, alertas y mejora continua \[7\], \[8\].                         |

El backend se recomienda en Python con FastAPI porque ofrece validación de modelos, integración natural con SQLAlchemy/PostgreSQL y una curva de desarrollo adecuada para una API académica que posteriormente puede crecer. El frontend se recomienda en TypeScript para mantener contratos de datos más explícitos entre interfaz y servicios web. El código Python seguirá las convenciones de PEP 8 \[13\].

Para evitar ambigüedad entre **tecnologías de desarrollo** y **servicios administrados de GCP**, esta sección define qué componentes deben implementarse realmente para construir y desplegar FindJob. La prioridad se basa en el alcance funcional definido en este documento y en el estado actual del proyecto.

#### A. Servicios base que forman parte del MVP

| Servicio / componente | ¿Se implementa? | Estado actual | Uso concreto en FindJob |
|---|---|---|---|
| **Cloud SQL for PostgreSQL 17** | **Sí, obligatorio** | **Implementado** | Persistencia relacional de las 36 tablas del esquema `marketplace`, integridad, transacciones y reglas de negocio. |
| **Cloud Run** | **Sí, obligatorio** | Desarrollo pendiente | Ejecutar el backend Python/FastAPI y publicar la API REST mediante HTTPS. |
| **Identity Platform / Firebase Authentication** | **Sí, obligatorio** | Planificado | Registro, inicio de sesión, recuperación de cuenta y emisión de ID tokens. FastAPI validará el token antes de operaciones protegidas. |
| **Firebase Hosting** | **Sí, obligatorio para el frontend web desplegado** | Por implementar | Publicar la SPA construida con React + TypeScript + Vite y servirla mediante HTTPS. |
| **Cloud Storage** | **Sí, obligatorio para el alcance funcional completo** | Planificado | Almacenar fotos, documentos y adjuntos del chat. PostgreSQL conservará únicamente metadatos y la ruta del objeto. |
| **Secret Manager** | **Sí, obligatorio al desplegar el backend** | Planificado / recomendado | Proteger credenciales de Cloud SQL, claves de integraciones y otros secretos sin almacenarlos en código o repositorios. |
| **Artifact Registry** | **Sí, para el despliegue del backend contenedorizado** | Por implementar | Almacenar y versionar las imágenes Docker que se desplegarán en Cloud Run. |
| **Cloud Logging** | **Sí** | Por configurar | Centralizar logs del backend, errores y eventos operativos; se recomienda logging estructurado. |
| **Cloud Monitoring** | **Sí, recomendado desde el MVP** | Por configurar | Supervisar disponibilidad, latencia, errores y recursos; permitir alertas operativas básicas. |
| **IAM y cuentas de servicio** | **Sí, transversal** | Por configurar junto con cada servicio | Aplicar mínimo privilegio entre Cloud Run, Cloud SQL, Storage, Secret Manager y demás recursos. |

> **Conclusión de implementación:** para que el MVP sea funcional de extremo a extremo no basta con Cloud SQL. Deben existir, como mínimo, **frontend desplegado, backend desplegado, autenticación, persistencia y almacenamiento de archivos**. Secret Manager, IAM y observabilidad deben configurarse en paralelo para que el despliegue sea técnicamente consistente y seguro.

#### B. Tecnologías que deben desarrollarse dentro de esos servicios

| Capa | Tecnología | Qué se debe construir |
|---|---|---|
| Frontend | **React + TypeScript + Vite** | Pantallas públicas, registro/inicio de sesión, perfiles, publicación y búsqueda de servicios, solicitudes, citas, chat, pagos simulados, calificaciones y seguridad presencial. |
| Backend | **Python + FastAPI** | Endpoints REST, validación de tokens, autorización por rol y por recurso, reglas de negocio, integración con PostgreSQL y Cloud Storage. |
| Persistencia | **SQLAlchemy** | Modelos/mapeos y consultas parametrizadas sobre PostgreSQL. |
| Migraciones | **Alembic** | Versionar cambios futuros del esquema sin modificar manualmente la base de datos. |
| Contenedores | **Docker** | Empaquetar FastAPI de forma reproducible para Cloud Run. |
| Contrato API | **OpenAPI** | Documentar endpoints, parámetros, esquemas y respuestas; FastAPI genera la base del contrato automáticamente. |

#### C. Automatización de construcción y despliegue

**Cloud Build** es el servicio recomendado en este diseño para CI/CD, pero no es estrictamente indispensable para una primera prueba manual. Si se adopta, deberá construir la imagen Docker, publicarla en Artifact Registry y desplegar la versión aprobada a Cloud Run. Como alternativa técnica puede utilizarse GitHub Actions, manteniendo Artifact Registry y Cloud Run como destino.

#### D. Servicios que no son necesarios en la primera versión

Los siguientes servicios deben incorporarse solo cuando una necesidad funcional concreta lo justifique:

- **Google Maps Platform:** geocodificación, mapas o selección visual de ubicación para servicios presenciales.
- **Cloud Tasks:** recordatorios, notificaciones o tareas diferidas que no deban ejecutarse dentro de la petición HTTP.
- **Pub/Sub:** eventos desacoplados si el sistema crece y requiere procesamiento asíncrono entre componentes.
- **Cloud Armor:** WAF y protección adicional para una etapa de producción real.
- **API Gateway:** no es necesario mientras FindJob mantenga un único backend monolítico en Cloud Run; podría incorporarse con múltiples APIs, consumidores o políticas centralizadas de cuota.
- **Pasarela de pago externa:** opcional en el alcance académico, porque el flujo de pagos puede simularse inicialmente.

#### E. Orden recomendado de implementación

1. **Mantener Cloud SQL como base ya implementada** y cargar los catálogos mínimos requeridos por las reglas del modelo.
2. **Construir el backend FastAPI localmente**, conectándolo a PostgreSQL mediante SQLAlchemy y gestionando cambios futuros con Alembic.
3. **Configurar IAM, cuenta de servicio y Secret Manager** antes del despliegue del backend.
4. **Crear Artifact Registry y desplegar el backend en Cloud Run**; incorporar Cloud Build cuando se automatice CI/CD.
5. **Configurar Identity Platform/Firebase Authentication** e integrar la validación de ID tokens en FastAPI.
6. **Construir el frontend React + TypeScript + Vite** y conectarlo únicamente con la API; desplegarlo en Firebase Hosting.
7. **Configurar Cloud Storage** para fotos/documentos/adjuntos y conectar sus metadatos con `archivos_adjuntos` y las entidades correspondientes.
8. **Configurar Cloud Logging y Cloud Monitoring** para errores, trazabilidad, latencia y disponibilidad.
9. **Implementar primero el flujo funcional principal:** usuario → perfil → servicio → solicitud → cita → comunicación → pago simulado → calificación.
10. **Añadir seguridad presencial y servicios opcionales** una vez que el flujo principal sea estable.

## 3.3 Flujo lógico de la solución

1.  El usuario accede al frontend alojado en Firebase Hosting.

2.  El frontend consume endpoints públicos de Cloud Run o solicita autenticación a Identity Platform.

3.  Tras autenticarse, el frontend envía el ID token al backend en cada operación protegida.

4.  FastAPI valida identidad, rol y propiedad/participación sobre el recurso.

5.  El backend consulta o modifica Cloud SQL mediante SQLAlchemy y transacciones.

6.  Los archivos se cargan a Cloud Storage; Cloud SQL conserva únicamente metadatos y ruta del objeto.

7.  Cloud Logging/Monitoring recibe información operativa y Secret Manager protege credenciales.

Cloud SQL se utiliza en lugar de instalar PostgreSQL manualmente en una máquina virtual porque el proyecto debe concentrarse en la lógica de negocio y el modelo de datos. El servicio administrado reduce tareas de mantenimiento del motor y facilita respaldo, monitoreo y operación \[2\]. La zona única actual es apropiada para desarrollo y sustentación; para producción real se requeriría reevaluar alta disponibilidad y recuperación.

## 3.6 Catálogo de endpoints y permisos por rol

La API se publicará bajo una ruta versionada, por ejemplo https://api.findjob.com/api/v1. Todos los endpoints expuestos al frontend utilizarán HTTPS. La autorización se aplicará en el backend y no únicamente en la interfaz. Como un usuario puede tener más de un rol, los permisos son acumulables; por ejemplo, una persona con roles CLIENTE y TRABAJADOR podrá consumir los endpoints habilitados para ambos. Este esquema aplica el principio de mínimo privilegio y autorización por recurso descrito en OWASP \[9\]-\[11\].

Los endpoints de autenticación (registro, inicio de sesión, recuperación de contraseña y emisión de tokens) serán administrados principalmente por Identity Platform/Firebase Authentication. FindJob consumirá la identidad resultante y expondrá endpoints propios para consultar o completar el perfil de negocio del usuario.

### 3.6.5 Reglas generales de autorización de endpoints

| **Regla**                                           | **Aplicación**                                                                                                    |
|-----------------------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| Público no significa anónimo para todo el sistema   | Solo búsquedas y consultas de catálogo/perfiles/servicios serán públicas.                                         |
| Autenticación obligatoria para postularse/contratar | POST /solicitudes requiere token válido; esta es una restricción central del proyecto.                            |
| Autorización por recurso                            | El backend verifica que el usuario sea propietario, participante o tenga el rol requerido; evita BOLA/IDOR \[9\]. |
| Roles acumulables                                   | CLIENTE y TRABAJADOR pueden coexistir en un mismo usuario mediante usuario_roles.                                 |
| No confiar en el frontend                           | Ocultar botones no constituye seguridad; el control se ejecuta nuevamente en FastAPI \[9\]-\[11\].                |
| Estados del flujo                                   | Aceptar, cancelar, iniciar, finalizar, pagar o calificar solo se permiten desde estados válidos del dominio.      |
| Paginación y límites                                | Endpoints de listas y mensajes utilizan paginación y límites para reducir consumo no controlado \[9\].            |
| Auditoría de acciones sensibles                     | Cambios administrativos, pagos y eventos de seguridad deben generar logs sin almacenar secretos \[7\]-\[11\].     |

# 4. Base de datos y criterios de diseño

La base de datos implementada contiene 36 tablas dentro del esquema marketplace. El DDL utiliza claves primarias BIGINT identity, claves foráneas, restricciones CHECK/UNIQUE, índices y triggers de integridad para reglas que dependen de varias tablas. La normalización y separación de dependencias se sustentan en principios clásicos del modelo relacional \[14\].

## 4.1 Principios de tercera forma normal

- Cada tabla representa un concepto o relación claramente delimitado.

- No se duplican atributos que pueden obtenerse por una relación: servicios guarda subcategoria_id, pero la categoría se obtiene desde subcategorias.

- Los roles y modalidades se modelan mediante relaciones N:M, evitando valores compuestos como AMBOS.

- La reputación del trabajador se deriva de las calificaciones; no se almacena un promedio redundante.

- La comisión se obtiene del pago y la política histórica aplicable; no se repite el porcentaje dentro de cada servicio.

- Los catálogos reutilizables separan estados, métodos, roles, tipos y modalidades del dato transaccional.

## 4.2 Convenciones de diseño

| **Elemento**  | **Convención**                                                                                        |
|---------------|-------------------------------------------------------------------------------------------------------|
| Nombres       | snake_case en español.                                                                                |
| PK            | \<entidad\>\_id, BIGINT GENERATED ALWAYS AS IDENTITY.                                                 |
| FK            | Mismo nombre semántico que la PK referenciada.                                                        |
| Fechas        | TIMESTAMPTZ para eventos con zona horaria.                                                            |
| Dinero        | NUMERIC(14,2); comisión NUMERIC(5,2).                                                                 |
| Texto corto   | VARCHAR con límite semántico.                                                                         |
| Texto extenso | TEXT para descripción, mensajes y comentarios.                                                        |
| Coordenadas   | NUMERIC(9,6) latitud y NUMERIC(10,6) longitud.                                                        |
| Actualización | Campos creado_en/actualizado_en y trigger genérico en entidades principales.                          |
| Borrado       | RESTRICT para información de negocio histórica; CASCADE principalmente en tablas puente/dependientes. |

**Restricciones relevantes:** CONSTRAINT uq_archivos_objeto UNIQUE (bucket, ruta_objeto) \| CONSTRAINT chk_archivos_nombre CHECK (btrim(nombre_original) \<\> '') \| CONSTRAINT chk_archivos_bucket CHECK (btrim(bucket) \<\> '') \| CONSTRAINT chk_archivos_ruta CHECK (btrim(ruta_objeto) \<\> '')

## 7.1 Relaciones clave del negocio

| **Relación**                                 | **Interpretación**                                                         |
|----------------------------------------------|----------------------------------------------------------------------------|
| usuarios 1 — 0..1 perfiles_trabajador        | Un usuario puede habilitar un único perfil profesional.                    |
| usuarios N — M roles                         | Una persona puede asumir varios roles sin atributo AMBOS.                  |
| usuarios N — M habilidades                   | Un usuario puede asociar múltiples habilidades reutilizables.              |
| categorias 1 — N subcategorias               | Cada subcategoría pertenece a una categoría.                               |
| perfiles_trabajador 1 — N servicios          | Un trabajador puede publicar múltiples servicios.                          |
| servicios N — M modalidades                  | Un servicio puede ser remoto, presencial o ambas modalidades por relación. |
| perfiles_trabajador N — M ciudades           | Cobertura geográfica para servicios presenciales.                          |
| usuarios 1 — N direcciones                   | Un usuario puede conservar varias direcciones reutilizables.               |
| servicios 1 — N solicitudes_servicio         | Un servicio puede recibir múltiples solicitudes.                           |
| solicitudes_servicio 1 — 0..1 citas          | El modelo actual programa como máximo una cita por solicitud.              |
| solicitudes_servicio 1 — 0..1 conversaciones | Una solicitud aceptada puede habilitar una conversación.                   |
| conversaciones 1 — N mensajes                | El chat conserva mensajes, lecturas y adjuntos.                            |
| citas 1 — 0..1 pagos                         | Un pago máximo por cita en el alcance actual.                              |
| citas 1 — 0..1 calificaciones                | Una calificación máxima por cita finalizada.                               |
| citas 1 — N alertas/chequeos                 | Las citas presenciales pueden producir múltiples eventos de seguridad.     |

# 8. Reglas de negocio implementadas en base de datos

| **Regla**                                           | **Mecanismo**                                                                        |
|-----------------------------------------------------|--------------------------------------------------------------------------------------|
| Perfil profesional solo para trabajador             | Trigger fn_validar_rol_trabajador verifica rol TRABAJADOR.                           |
| Modalidad válida para servicio                      | FK compuesta solicitudes_servicio(servicio_id, modalidad_id) → servicio_modalidades. |
| No contratar servicio propio                        | Trigger fn_validar_solicitud_contexto.                                               |
| Solicitud presencial requiere dirección del cliente | Trigger fn_validar_solicitud_contexto.                                               |
| Solicitud remota no usa dirección                   | Trigger fn_validar_solicitud_contexto.                                               |
| Cita presencial/remota coherente                    | Trigger fn_validar_cita_contexto.                                                    |
| Chat solo después de aceptar solicitud              | Trigger fn_validar_conversacion_solicitud.                                           |
| Solo cliente y trabajador en conversación           | Trigger fn_validar_participante_conversacion.                                        |
| Lecturas solo de participantes                      | Trigger fn_validar_lectura_participante.                                             |
| Seguridad solo para cita presencial                 | Triggers de alerta, chequeo y respuesta.                                             |
| Calificar solo cita finalizada                      | Trigger fn_validar_calificacion_finalizada.                                          |
| Pago solo cita finalizada                           | Trigger fn_validar_pago.                                                             |
| Política de comisión vigente                        | fn_validar_pago verifica fecha contra vigencia.                                      |
| No solapamiento de políticas                        | EXCLUDE USING gist sobre rango temporal.                                             |
| No alterar política ya usada                        | Triggers fn_proteger_politica_comision_usada.                                        |
| Actualización automática de timestamps              | fn_actualizar_timestamp en entidades principales.                                    |
