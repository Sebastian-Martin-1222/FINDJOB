# Revisión UX y funcional previa a despliegue — FindJob

## Resultado ejecutivo

La interfaz tiene una base visual consistente y una navegación comprensible, pero el flujo de primera vez requería mejoras para evitar que estados normales se presentaran como errores. También se detectaron dos bloqueadores funcionales que afectaban directamente la experiencia: el trigger de creación de perfil profesional y la persistencia de contraseñas de cuentas nuevas.

## Correcciones aplicadas

### Prioridad crítica
- Se agregó persistencia de `password_hash` para nuevas cuentas. Antes, el hash se guardaba solo en memoria del proceso y podía perderse al reiniciar/escalar Cloud Run.
- Se corrigió `marketplace.fn_validar_rol_trabajador()` para referenciar `marketplace.usuario_roles` y `marketplace.roles` explícitamente.
- Se agregó una migración idempotente en `backend/migrations/20261108_profile_auth_fix.sql` para la base ya desplegada.

### UX / onboarding
- El dashboard profesional ya no trata la ausencia de perfil como un error técnico; muestra un CTA claro para completarlo.
- Publicar servicio valida primero que exista el perfil profesional y evita hacer llenar un formulario que luego sería rechazado.
- `Perfil de servicios` pasa a `Perfil profesional`; `Mi perfil` pasa a `Mi cuenta` para diferenciar mejor ambos espacios.
- El formulario de perfil profesional incluye ayudas, campos obligatorios claros y confirmación de guardado.
- El estado vacío de servicios incluye CTA para publicar el primero.
- Se reemplazaron mensajes que exponían clasificaciones internas innecesarias en la experiencia principal.

### Navegación pública y consistencia
- Se corrigieron enlaces públicos que apuntaban a rutas inexistentes (`/como-funciona`, `/trabajador/registro`).
- El buscador de portada y las tarjetas de categorías ahora sí afectan el catálogo; antes generaban parámetros que la página de servicios ignoraba.
- Se eliminó la ubicación fija `Bogotá D.C., Chapinero`, que podía inducir a error; se muestra `Colombia`.
- La promoción de Comunidades se sustituyó por una sección real de `Cómo funciona`, porque Comunidades está explícitamente fuera de alcance productivo.
- Los errores 401 públicos ahora priorizan el mensaje real del backend; un login incorrecto deja de parecer una sesión expirada.

## Pendientes no modificados

- La sesión se almacena en memoria; recargar completamente la página obliga a autenticarse nuevamente. Esto es una decisión de seguridad/arquitectura documentada y cambiarla correctamente requeriría cookie HttpOnly/BFF o equivalente.
- Los usuarios legados sin `password_hash` conservan temporalmente la contraseña semilla `Password123!` por compatibilidad. Para un entorno productivo real se recomienda implementar restablecimiento/cambio de contraseña y eliminar ese fallback.
- Dependencias frontend reportan vulnerabilidades/deprecaciones; no se ejecutó `npm audit fix --force` para evitar cambios mayores no controlados antes de la entrega.
